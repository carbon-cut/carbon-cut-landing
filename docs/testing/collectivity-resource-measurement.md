# Collectivity resource measurement protocol

Status: agreed approach for [landing issue #102](https://github.com/carbon-cut/carbon-cut-landing/issues/102). The first local split-host profile is recorded in [the local run report](./collectivity-resource-measurement-local-run.md). The [preceding research](https://github.com/carbon-cut/carbon-cut-landing/issues/101) found that the archived Household benchmark and the single-project Sfax integration test cannot size active Collectivity.

## Purpose and limits

Measure the current Collectivity journey quickly enough to inform deployment work. The first run uses production-mode Next.js and Strapi in WSL with the existing PostgreSQL **test database on Windows**. It gives an observed load/latency/resource curve for that split machine, not a Hetzner VM capacity claim. Next.js and Strapi Docker images, with a pinned PostgreSQL image, are planned before deployment. Reuse this workload against those images when available. Do not hold up subsequent deployment work for a candidate-host benchmark; carry the remaining sizing uncertainty into that decision.

Capacity in this report means an **observed active-session range for a stated journey and data size**. Total registered users cannot be inferred without an assumption about actions per active user and peak-hour activity. There is no predetermined pass/fail threshold; report the load step at which latency, errors, or resource pressure visibly change, without turning that observation into a guarantee.

## Build the reusable measurement harness

1. Create a fixture-preparation script and a timed HTTP driver. Keep both independent of application runtime behavior. Reuse the Sfax inventory as a realistic starting payload, but create distinct synthetic users, subscriptions, projects, inventories, and existing calculation results. Start with roughly 25 Sfax-sized projects; record actual payload, row, and database sizes. Give concurrent sessions different project records so they do not contend on one shared inventory by accident. Use disposable credentials and a resettable fixture state.
2. Make fixture preparation explicitly target the backend's PostgreSQL test database. Run `npm run test:integration:verify-db` from the backend first. The script must independently confirm its connected database name before any write or reset. Do not run another integration suite against that database during measurement. Preserve a known fixture snapshot or reproducible reset procedure so each load step begins from comparable data.
3. Run Strapi with `NODE_ENV=production` and PostgreSQL, and run built Next.js with `next start`, MSW disabled, and its same-origin API routes pointing to Strapi. **Production Strapi does not read `DATABASE_TEST_*`.** In the measurement launcher, map the verified test connection into the corresponding `DATABASE_*` values, clear `DATABASE_URL`, and confirm the running process connects to `DATABASE_TEST_NAME`. Never let the production-mode process fall back to SQLite or the normal PostgreSQL database. This mapping is for the local experiment, not a change to Strapi's database configuration.
4. Obtain normal authenticated sessions for the synthetic users. Test-only auth support and development seeding are disabled in production mode. Smoke-test one sign-in, inventory read, draft save, calculation, and stored result read before timed traffic. Verify the calculation succeeded and the stored result belongs to the intended project.
5. Drive the same-origin Next.js routes with separate sessions and realistic pauses. Mix sign-in/session and project navigation, inventory reads, draft saves, occasional calculations, and result reads. Include some calculations overlapping across different projects. Record operation counts and rates by type. Quote, subscription, and setup actions may be added when their fixtures are ready; list any omitted active flows in the report.

The current `test:integration` runner is a functional setup, not the measurement launcher: it starts Strapi in test mode and Next.js in development mode. The existing Sfax browser test is a useful request-path reference, but exercises one user and project.

## Run and record

- Record both repository commits, build commands, Node versions, WSL and Windows versions, CPU/RAM available to each, PostgreSQL version, database connection/pool settings, test database size, project and inventory counts, and whether each reading is cold or warm.
- Capture an idle baseline. Run bounded steps of **1, 3, 5, then 10 active sessions** with the same scripted action mix and think-time distribution. Warm each step before recording a timed window; record the actual warm-up and measurement durations. Stop a step if errors, timeouts, or resource exhaustion make further traffic uninformative. Repeat an interesting step from the reset fixture to check that the observation is reproducible.
- For each operation, record request count, requests per second, p50/p95/p99 latency, errors/timeouts, and calculation duration. Record Next.js and Strapi CPU and RSS/working-set memory, WSL-wide CPU/memory/swap and restarts, and Windows PostgreSQL CPU/memory, active connections, database size, reads/writes, and disk pressure where available. Sample at a fixed interval and state that interval. Do not add backend pool instrumentation merely to complete the first pass.
- Keep the driver from materially consuming the same WSL resources being attributed to the apps, or measure and report its overhead. Record whether a load step was limited by the driver, WSL resource limits, the Windows host, the database, or the application.
- Report the observed active-session range alongside action rate, payload/data size, latencies, errors, and per-process resource use. If translating it to a broader user estimate, state the assumed actions per active user and peak-hour share. Mark this first report **local split-host estimate**; it cannot be used as a direct all-in-one Hetzner RAM or CPU requirement.

## Result handoff

Save the fixture and driver revisions, exact commands and non-secret configuration, raw timing and resource samples, summary table, and known limits with the issue. Record any missing measurement rather than filling it with the archived Household figures. When the Docker images are built, run the same fixture and driver against them and label those results separately. A candidate-host run can later validate a particular Hetzner size; it is not required to move past this initial local profile.
