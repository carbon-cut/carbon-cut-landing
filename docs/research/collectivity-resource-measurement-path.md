# Measuring Collectivity resource demand before server sizing

Research for [Find a safe resource measurement path for active Collectivity](https://github.com/carbon-cut/carbon-cut-landing/issues/101). Source revisions: frontend `4a46b6da3b68bad1f233b64b14d620e3aeafb0c4`; backend `33ccbc7e663034ae73bb72f40b7f8624f29233a2`. This is a proposed experiment, not a capacity result. No load test was run.

## Evidence available now

- The archived backend benchmark reports Strapi RSS/CPU, DB pool use and pending acquisitions, request rate, latency percentiles, and errors for short concurrency sweeps. Its March report used PostgreSQL and a production Strapi boot on WSL2, but the form workload uses retired `POST /api/carbon-footprint/forms/basic` and omits Next.js, active Collectivity, and PostgreSQL server resource use. Its 297.71 MB idle Strapi RSS is only a historical reference, not a sizing floor for this deployment. [Backend benchmark guide](https://github.com/carbon-cut/carbon-cut-backend/blob/33ccbc7e/docs/operations/local-benchmarking.md), [runner](https://github.com/carbon-cut/carbon-cut-backend/blob/33ccbc7e/scripts/benchmark/local-benchmark.js), [archived report](https://github.com/carbon-cut/carbon-cut-backend/blob/33ccbc7e/reports/benchmarks/local-benchmark-latest.md).
- A substantial Sfax inventory fixture (~47 KB of JS source) and expected result comparison exist. The backend Sfax test creates or repairs a user, active entitlement, project, inventory and country parameters, then saves, calculates, and reads results. The frontend Sfax browser test signs in and exercises save, project GET, UI calculation, and result GET through same-origin API routes. These prove a functional path, not performance or representative dataset size. [Fixture](https://github.com/carbon-cut/carbon-cut-backend/blob/33ccbc7e/tests/carbon-footprint/tunisia/sfax-dev-inventory.js), [backend test](https://github.com/carbon-cut/carbon-cut-backend/blob/33ccbc7e/tests/carbon-footprint/collectivity/integration/sfax-inventory.test.js), [browser test](https://github.com/carbon-cut/carbon-cut-landing/blob/4a46b6da/tests/collectivity/inventory/end-to-end/sfax-inventory-browser.mjs).
- The current integration runner verifies a distinct PostgreSQL test database and runs Strapi in test mode, but starts Next.js with `next dev --turbopack`. It does not build or run Next.js in production mode, seed default factors, or capture process/DB metrics. [Runner](https://github.com/carbon-cut/carbon-cut-landing/blob/4a46b6da/scripts/run-integration.mjs), [README](https://github.com/carbon-cut/carbon-cut-landing/blob/4a46b6da/README.md).

## Smallest safe production-mode experiment

1. Use an **ephemeral, isolated Linux environment** with a private PostgreSQL database, no real customer data, no public writes, and resource limits recorded. One temporary Hetzner Cloud VM can run Next.js, Strapi, PostgreSQL, and a private load driver for a first aggregate test; a separate load driver is preferable if the VM saturates. Record VM type, vCPU/RAM, disk, OS, Node version, app commits, DB pool settings, dataset size, and cold/warm state. This VM tests a candidate size; it is not the final topology decision.
2. Prepare an isolated database before the measurement. Reuse the Sfax fixture and backend Sfax setup/parameter seed as a starting fixture; create enough **separate users, subscriptions, projects, inventories, and historical calculation rows** to approximate plausible launch data volume. Use distinct project slugs and users for concurrent writes, and a resettable database snapshot. Decide the user count and record counts from an explicit workload assumption before generating them. Avoid rerunning the same Sfax calculation against one shared row as a concurrency proxy. [Sfax setup](https://github.com/carbon-cut/carbon-cut-backend/blob/33ccbc7e/tests/carbon-footprint/collectivity/integration/sfax-inventory.test.js), [dev seed](https://github.com/carbon-cut/carbon-cut-backend/blob/33ccbc7e/src/dev-seed/integration.js).
3. Build both apps, run Strapi with `NODE_ENV=production` and PostgreSQL `DATABASE_*`, and run `next start` with MSW off and `BACKEND_URL` pointing to private Strapi. Keep the same-origin Next.js route path. **Do not assume the existing test bootstrap can prepare a production process:** dev integration seeding and auth test-support routes are disabled in production, while `DATABASE_TEST_*` is selected only by test mode. A one-time fixture preparation script or snapshot import into a dedicated experiment database is needed; verify the database target before any preparatory write. [Backend database config](https://github.com/carbon-cut/carbon-cut-backend/blob/33ccbc7e/config/database.ts), [seed gate](https://github.com/carbon-cut/carbon-cut-backend/blob/33ccbc7e/src/dev-seed/integration.js), [test-support gate](https://github.com/carbon-cut/carbon-cut-backend/blob/33ccbc7e/src/utils/auth-test-support.js), [frontend scripts](https://github.com/carbon-cut/carbon-cut-landing/blob/4a46b6da/package.json).
4. First smoke-test the Sfax save/calculation/result path once. Then run a bounded, gradually stepped **mixed journey**: sign-in/session and project navigation, inventory GET, draft PUT, result GET, and occasional calculation POST; add setup and quote/claim at a realistic low frequency when their fixtures are ready. Include think time and separate per-user sessions; track operation mix and request rate, not only concurrent HTTP connections. The existing browser test provides a request sequence but would need a purpose-built driver for timed traffic. [Frontend Sfax test](https://github.com/carbon-cut/carbon-cut-landing/blob/4a46b6da/tests/collectivity/inventory/end-to-end/sfax-inventory-browser.mjs), [same-origin calculate route](https://github.com/carbon-cut/carbon-cut-landing/blob/4a46b6da/src/app/api/collectivity/projects/%5BprojectSlug%5D/current-inventory/calculate/route.ts), [save route](https://github.com/carbon-cut/carbon-cut-landing/blob/4a46b6da/src/app/api/collectivity/projects/%5BprojectSlug%5D/current-inventory/input/route.ts).
5. At idle and every load step, capture each app's CPU, RSS/working-set memory and restarts/OOM; whole-VM CPU, memory, swap, disk I/O and space; PostgreSQL process memory/CPU, connections (`pg_stat_activity`), transaction rate, cache-hit/read/write and deadlocks (`pg_stat_database`), database size; and request p50/p95/p99, errors/timeouts and throughput by operation. If enabled on this isolated database, `pg_stat_statements` can identify expensive SQL. The old worker's Knex pool sampler can be adapted to report used/free/pending acquisitions from Strapi, but that is an **optional backend code change** for a second pass, not a prerequisite to the first measurement. [Old sampler](https://github.com/carbon-cut/carbon-cut-backend/blob/33ccbc7e/scripts/benchmark/strapi-worker.js), [pool defaults](https://github.com/carbon-cut/carbon-cut-backend/blob/33ccbc7e/config/database.ts).
6. Stop at a predefined error/latency limit or resource pressure; repeat the useful load points with longer steady-state runs and a clean snapshot. Report the largest *measured* workload meeting explicit latency/error and resource-headroom criteria, together with traffic mix and dataset size. Then translate observed requests per active session and assumed peak-hour fraction into estimated active users. A single benchmark run cannot establish a guarantee or a raw registered-user limit.

## Work and access needed before running it

- A temporary Hetzner account/project budget and private VM/network access; a separate test database and disposable credentials; build/deploy access to both repositories; an agreed synthetic user/data scale and traffic mix. Do not connect the driver to production or a shared development database.
- A small **fixture-preparation and load-driver implementation** is likely needed. Existing Sfax test setup and comparison are reusable, but the integration runner is not a production-mode harness, the fixture is one project, and the archived benchmark targets Household. A dedicated PostgreSQL database can be prepared in test mode and then used by a production-mode app only after explicit target verification; a separate import/setup script may be clearer and safer. Any new prep script should have an explicit database allowlist and be reviewed before use.
- No backend runtime modification is necessary for a first black-box pass. Pool telemetry, SQL tracing, and more realistic fixture generation may justify later backend or test-harness changes. Fixing the server layout before this measurement would turn unknown resource needs into an untested assumption.
