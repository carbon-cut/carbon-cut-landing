# Collectivity data recovery options for launch

Researched 20 October 2026 for [Compare data recovery options and costs for the launch target](https://github.com/carbon-cut/carbon-cut-landing/issues/99). This compares ways to protect **database saves already confirmed to a user** after loss of the primary server. It does not select a target or claim that a two-hour restoration is already achievable. All prices below are indicative, exclude tax, and require checkout confirmation. Server sizing and actual database size remain unknown.

## Decision in plain language

| Desired maximum recent data loss | Plausible launch design | Illustrative added monthly spend beyond one primary server | What remains to prove |
| --- | --- | --- | --- |
| **Up to 1 hour** | PostgreSQL base backup plus continuous write-ahead log (WAL) archive to off-server object storage. Force a WAL segment switch no later than about 30 minutes; alert if the most recent *successfully uploaded* WAL is too old. | Backblaze B2 at **$6.95/TB/month**, with the first 10 GB free; at 100 GB stored, roughly **$0.70/month** before any chargeable egress. Add optional Hetzner Cloud daily server backup at **20% of primary price**, e.g. **€7.10/month** for a €35.49 CPX32. | Complete restore, including app and DNS/network steps, under two hours at measured data size. Continuous monitoring and a buffer below the one-hour target are necessary. |
| **Up to 15 minutes** | Same base-backup/WAL design, forcing segment switches around every 5 minutes and alarming when the uploaded recovery point lags. An asynchronous warm standby is an alternative if recovery from archive is too slow. | The object-storage base price is essentially unchanged at small data sizes, but more frequent WAL uploads and possibly a second server add cost. Example standby: another CPX32 **€35.49/month**, plus its backup and storage if used. | Archive transfer may stall; a scheduled switch alone is **not** a hard 15-minute guarantee. Restore test must include the final archived WAL and meet the two-hour clock. |
| **Every confirmed database save after loss of one server** | PostgreSQL **synchronous** standby on a separate server, with `synchronous_commit=on` and a named synchronous standby. Keep separate point-in-time backups for accidental deletion/corruption. | At least a second suitable server: illustrative second CPX32 **€35.49/month**, so two CPX32s are **€70.98/month** before backup storage, IPs, traffic or app redundancy. | Promotion, connection cutover and application recovery under two hours; commit latency; behavior when the standby is down; separate backups. Hetzner bills optional Cloud backups at 20% of server price for seven slots. [Hetzner billing FAQ](https://docs.hetzner.com/cloud/billing/faq/).

## Why these choices differ

PostgreSQL base backups plus WAL can restore to a point covered by **available archived WAL**. WAL archiving normally ships complete segments, and `archive_timeout` can limit time before a segment switch; it cannot ensure that a failed upload has reached the backup destination. The monitoring condition must therefore use the latest safely stored WAL, not merely the last scheduled backup. [PostgreSQL point-in-time recovery](https://www.postgresql.org/docs/current/continuous-archiving.html), [PostgreSQL standby and log shipping](https://www.postgresql.org/docs/current/warm-standby.html). Backblaze's current published B2 rate is $6.95/TB/month, with 10 GB free and free egress up to 3× average monthly stored data. Its price is usage-based, so WAL volume, retention, and restore downloads must be measured. [Backblaze pricing](https://www.backblaze.com/cloud-storage/pricing).

An asynchronous standby may recover service faster than rebuilding a server, but PostgreSQL says commits can be lost if the primary fails before they reach it. With synchronous replication, a write is acknowledged only after WAL is durably written on the chosen standby. This protects acknowledged database commits against **one** primary-server loss, provided the app acknowledges only after commit. If that standby is unavailable, writes wait rather than silently dropping the protection; the owner must decide whether to accept a write outage or temporarily weaken the rule. It also increases write latency and needs careful failover to avoid two writable primaries. [PostgreSQL standby and synchronous replication](https://www.postgresql.org/docs/current/warm-standby.html), [PostgreSQL replication configuration](https://www.postgresql.org/docs/current/runtime-config-replication.html).

Neither replication nor a provider disk image replaces independent database backups. Replication can faithfully copy deletion or corruption. Hetzner Cloud backups are daily disk copies with seven slots; a restore loses later data, and attached Volumes are excluded. Treat them as server rebuild aids, not as a 15-minute/one-hour database recovery mechanism. [Hetzner backup overview](https://docs.hetzner.com/cloud/servers/backups-snapshots/overview/), [Hetzner Volume overview](https://docs.hetzner.com/cloud/volumes/overview/). A second copy outside the Hetzner account/provider reduces shared-account and provider incidents; the existing local note proposed Backblaze, but no destination has been approved for launch.

## Operational and one-time cost

The dominant one-time cost is **setup and rehearsal time**, not a listed service fee. A single IT owner must automate base backups/WAL retention, protect credentials, test a clean restore, document the cutover, and arrange alerts that reach them. The synchronous option additionally needs replication setup, lag/health checks, planned promotion and fencing, and regular drills. PostgreSQL explicitly notes that restoring from archive takes considerably longer than activating a warm standby. [PostgreSQL standby guidance](https://www.postgresql.org/docs/current/warm-standby.html). No credible person-hour figure is available without database size, deployment topology, and a timed drill.

For the **under-two-hour outage target**, start the clock at user-visible failure and stop only when a user can complete a real Collectivity save/read again. Test at least primary-node loss and a bad deployment, including detection, owner response, infrastructure start, data restore or standby promotion, app start, routing, and verification. If response is expected outside staffed hours, one person's availability is a separate unresolved risk even if the technology restores quickly. Any confirmed saves held outside PostgreSQL (uploads, object storage, queues) require their own recovery design. The blueprint should not promise either time or data-loss target until a drill demonstrates it at a representative data size.
