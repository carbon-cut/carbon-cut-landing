# Collectivity workload audit for deployment planning

Research for [Audit active Collectivity workloads and the existing Strapi benchmark](https://github.com/carbon-cut/carbon-cut-landing/issues/92), 20 October 2026. This is a source audit, not a load test or capacity estimate. Frontend source was read at `4a46b6da`; backend source at `33ccbc7e`.

## Production workload to represent

The implemented Collectivity journey runs from pricing and quote through subscription access, project creation, setup, inventory draft, calculation, and result viewing. The project route map explicitly excludes undeveloped navigation destinations from product scope. [Frontend route map](https://github.com/carbon-cut/carbon-cut-landing/blob/4a46b6da/docs/collectivity/product/routes.md)

| --- | --- | --- |

The project list is loaded during server rendering and also checks available claims. Browser mutations and queries use the same-origin Next.js API layer. Its calculate route checks the session and project access before forwarding to Strapi. Server-rendered pages also load backend data. End-to-end user latency therefore needs a Next.js-to-Strapi test, while a direct Strapi test can isolate backend cost. ## What the archived benchmark establishes

The saved report records one local run: Strapi v4.23.1 in `production` mode, PostgreSQL, Node 20.19.4, WSL2, with 5/10/20 closed-loop concurrent requests for 20 seconds per scenario. It records request rate, latency percentiles, errors, Strapi RSS/CPU, and DB pool use. Its c20 login was 13.53 requests/s at 1.63 s p95; the `form-submit` run was 24.35 requests/s at 897 ms p95 with 69 pending DB acquires. These are **historical observations under this setup**, not supported-user or deployment-size figures. The DB configuration defaults to a maximum pool of 10. [Saved report](https://github.com/carbon-cut/carbon-cut-backend/blob/33ccbc7e/reports/benchmarks/local-benchmark-latest.md), [runner defaults](https://github.com/carbon-cut/carbon-cut-backend/blob/33ccbc7e/scripts/benchmark/local-benchmark.js#L15-L28), [DB configuration](https://github.com/carbon-cut/carbon-cut-backend/blob/33ccbc7e/config/database.ts#L86-L125)

The runner has reusable measurement machinery and auth lifecycle scenarios, but its application scenarios send `POST /api/carbon-footprint/forms/basic` and repeatedly fetch one `/api/carbon-footprint/responses/uid/:uid`. Those are the **retired Household service**: the plugin no longer registers its public routes. The default form body is deliberately minimal; the run used no custom payload. Its email worker stubs outgoing sends, so registration and recovery timings omit provider latency. The runner sends directly to Strapi, excluding Next.js rendering, proxy/session work, browser assets, TLS/proxy overhead and production network effects. [Runner scenarios](https://github.com/carbon-cut/carbon-cut-backend/blob/33ccbc7e/scripts/benchmark/local-benchmark.js#L833-L901), [Household request definitions](https://github.com/carbon-cut/carbon-cut-backend/blob/33ccbc7e/scripts/benchmark/local-benchmark.js#L1144-L1173), [unregistered routes](https://github.com/carbon-cut/carbon-cut-backend/blob/33ccbc7e/src/plugins/carbon-footprint/server/routes/index.ts#L16-L29), [retirement note](https://github.com/carbon-cut/carbon-cut-backend/blob/33ccbc7e/docs/household-footprint.md), [email stub](https://github.com/carbon-cut/carbon-cut-backend/blob/33ccbc7e/scripts/benchmark/strapi-worker.js#L150-L171)

The saved run is from 30 March 2026 and the current route registration is newer. Its successful Household responses must not be assumed reproducible today. Even when those routes existed, a repeated fetch of one seed response did not represent distinct Collectivity projects, realistic inventory sizes, parameter cardinality, revision history or concurrent calculations. [Saved report JSON](https://github.com/carbon-cut/carbon-cut-backend/blob/33ccbc7e/reports/benchmarks/local-benchmark-latest.json), [seed and request generation](https://github.com/carbon-cut/carbon-cut-backend/blob/33ccbc7e/scripts/benchmark/local-benchmark.js#L879-L901), [scenario loop](https://github.com/carbon-cut/carbon-cut-backend/blob/33ccbc7e/scripts/benchmark/local-benchmark.js#L1175-L1190), [backend project lifecycle](https://github.com/carbon-cut/carbon-cut-landing/blob/4a46b6da/docs/collectivity/architecture/project-lifecycle.md)

## Evidence needed for a capacity claim

1. Define a **mixed journey model**: active sessions, actions per session/hour, proportions of quote/setup/read/draft/calculate/result traffic, payload sizes and project/parameter data sizes; distinguish ordinary and burst periods. These inputs are product assumptions to validate, not derivable from the benchmark.
2. Use authorized, representative Collectivity accounts/projects and multiple realistic inventory payloads (small and large, varied years/applicability). Measure successful saves and calculations, including result checks and persistence growth. Keep the old runner's sampling/percentile approach, but replace retired scenarios and ensure fixture setup/teardown is isolated. [Current routes](https://github.com/carbon-cut/carbon-cut-backend/blob/33ccbc7e/src/collectivity/projects/routes.js), [runner metrics](https://github.com/carbon-cut/carbon-cut-backend/blob/33ccbc7e/docs/operations/local-benchmarking.md)
3. Run both isolated Strapi and full Next.js→Strapi journeys on a production-like Linux setup with the proposed CPU/RAM, DB/storage, connection pool, network, mail and proxy configuration. Record p50/p95/p99, errors, throughput, CPU/RSS, DB pool wait/CPU/queries, request sizes, and calculation duration. Include sustained and burst tests, recovery after load, and a clear stop threshold. The local guide itself says WSL2 CPU sizing is provisional and calls for a production-like Linux validation. [Local benchmark guide](https://github.com/carbon-cut/carbon-cut-backend/blob/33ccbc7e/docs/operations/local-benchmarking.md), [saved report](https://github.com/carbon-cut/carbon-cut-backend/blob/33ccbc7e/reports/benchmarks/local-benchmark-latest.md)
4. State capacity as the **tested workload at an explicit response-time/error target and resource headroom**, then translate it to estimated active users using the stated actions/session and burst factor. Total registered users alone does not specify load. This is the proposed inference method; no defensible number is available from current evidence.
